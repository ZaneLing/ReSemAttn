# ReSemReason

Reference implementation of **ReSemReason**, a relation-semantic reasoning framework for biomedical multi-hop question answering.

The implementation follows the four-stage pipeline described in the paper:

1. **Question understanding**: uncertain entity grounding and question-only soft relation-schema prediction.
2. **Relation-guided search**: schema-aware beam search that discovers candidate answers rather than reranking a fixed candidate pool.
3. **ReSemAttn reasoning**: path memories encode entities, directed relations, path structure, and topology; relation semantics condition key/value projections and provide an attention prior.
4. **Multi-path prediction**: evidence from multiple paths is aggregated into candidate scores and a calibrated answer set.

> **Status.** This repository is a clean research reference implementation reconstructed from the method specification. It is runnable on the included toy graph and provides the interfaces needed for BioHopR, PrimeKGQA, MedReason-Heldout, and PrimeKG adapters. Dataset redistribution, official preprocessing scripts, and measured paper checkpoints are not included.

## Quick start

Run the complete framework on the included biomedical toy graph:

```bash
python scripts/run_inference.py \
  --config configs/default.yaml \
  --question "Which adverse effects are linked to drugs used to treat rheumatoid arthritis?"
```

Expected output contains:

- grounded anchor entities and probabilities;
- top soft relation schemas;
- candidate answers discovered by graph search;
- candidate scores;
- highest-scoring supporting paths.

Evaluate the toy set:

```bash
python scripts/evaluate.py --config configs/default.yaml
```

Run a small training smoke test:

```bash
python scripts/train.py --config configs/default.yaml --epochs 3
```

## Data format

### Entities

One JSON object per line:

```json
{"id":"disease:ra","name":"rheumatoid arthritis","type":"disease","aliases":["RA"]}
```

### Directed edges

```json
{"source":"drug:methotrexate","relation":"indication","target":"disease:ra","provenance":"toy"}
```

The loader creates inverse traversal records internally. The original relation family is preserved and direction is represented as `+1` for the stored direction and `-1` for inverse traversal.

### Questions

```json
{
  "id":"q1",
  "question":"Which adverse effects are linked to drugs used to treat rheumatoid arthritis?",
  "gold_answers":["effect:nausea"],
  "gold_anchors":["disease:ra"],
  "gold_schemas":[{
    "hops":2,
    "entity_types":["disease","drug","effect"],
    "relations":["indication","side_effect"],
    "directions":[-1,1]
  }]
}
```

## PrimeKG and benchmark integration

Create the following three files from a frozen PrimeKG snapshot:

```text
data/primekg/entities.jsonl
data/primekg/edges.jsonl
data/<benchmark>/questions.jsonl
```

Then update `data.*` paths in the YAML configuration. The code does not assume a fixed candidate answer list. Candidate endpoints are generated by relation-guided search.

For BioHopR, public relation-hop and type fields may be converted to training supervision, but validation and test inference should pass only the natural-language question to the schema predictor. This avoids test-time schema leakage.

For PrimeKGQA, execute the gold SPARQL query against the same frozen PrimeKG snapshot to construct gold answer sets. For MedReason, define a source-disjoint held-out split before evaluation.

## Model configuration

The default configuration uses an offline trainable hashing encoder so the repository runs without downloading weights. To use Llama 3.1 hidden states, install the optional dependencies and select:

```yaml
encoder:
  backend: huggingface
  model_name: meta-llama/Llama-3.1-8B-Instruct
  torch_dtype: bfloat16
  freeze: false
```

Access to gated Meta weights and adequate GPU memory are required. For four 24 GB RTX 4090 GPUs, use Accelerate, FSDP, ZeRO, or quantized loading according to your training setup. The reference code intentionally does not hard-code one distributed launcher.

## Training stages

The paper's staged optimization can be reproduced as follows:

1. Train entity grounding and question-only schema induction.
2. Train the local search scorer and path-aware answer reasoner using positive paths and matched reachable-but-invalid negatives.
3. Jointly fine-tune differentiable modules with pointwise, pairwise, listwise, path, and calibration objectives.

The discrete top-B beam operation is not differentiated through. Gradients update the local extension scorer from supervised positive and negative extensions.

## Core equations implemented

Search score:

```text
lambda_g log p(anchor|q)
+ lambda_s Compat(q, path)
+ lambda_q Sem(q, endpoint)
- lambda_h Hub(endpoint)
```

Schema-marginalized path compatibility:

```text
logsumexp_m [ log rho_m - D(schema_m, path) ]
```

ReSemAttn:

```text
softmax_k(
  q_t^T k_ik / sqrt(d)
  + lambda_l * confidence(q) * log(path_prior_ik + eps)
)
```

Candidate score:

```text
MLP(candidate-aware language state)
+ mu * [logsumexp(path compatibility) - log(number of paths)]
```

## Reproducibility notes

- Set random seeds in the configuration.
- Freeze the KG snapshot and preprocessing version.
- Use the same maximum hop count, beam width, retained-path cap, backbone, evaluator, and data split for controlled comparisons.
- Report means and standard deviations over multiple seeds.
- Path-validity evaluation should use blinded, independent annotations rather than model-derived schema labels.
- Do not treat attention weights or retrieved paths as causal or clinical explanations.
